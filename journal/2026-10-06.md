## 2026-10-06_10:28:10 - Draft: the document model in RDF 1.2

The user asked how the triplifier output would look in RDF 1.2, to separate data from annotation. Inputs: this repo and `shapes/document.ttl` in [model](osg://repo/192.168.68.58/OS/model). This is a draft only. The user takes no decisions now and asked to stay on the serialization, not on implementation. No code or shape was changed.

### Problem in the current output

Headings, parts and canvas anchors have selectors (location in the text). Asserted triples do not. A field `knows :: [[Bob]]` gives `<Alice> knows <Bob>` with no line or quote. A canvas edge gives `<Bob> lives_in <BobHouse>` and loses the edge id and the canvas.

### Draft rule (v3)

Full draft: [2026-10-06-rdf12-draft.ttl](2026-10-06-rdf12-draft.ttl). Excerpt below.

- A triple stated by a span of text gets a reifier (`~`). The data triple is unchanged.
- Reifier IRI: `urn:reference:<subject>:quote:<text>`. `resource:source` is the subject of the triple. The reifier is a `resource:ResourceReference` with the existing `urn:selector:` selectors: RFC 5147 line (where) and text quote (what). No line number in the IRI, so that an edit above it does not change the IRI.
- A canvas edge: the reifier is `urn:name:<board>.canvas%23<edgeId>`, with the JSON Canvas id selector and the label as a quote.
- Structural triples (`rdf:type`, `schema:about`, `resource:source`, `resource:selector`) and group containment (`dct:hasPart`, derived from rectangles) get no reifier.
- No blank nodes.

```turtle
VERSION "1.2"
<urn:name:Alice> <urn:token:knows> <urn:name:Bob>
  ~ <urn:reference:urn%3Aname%3AAlice:quote:knows%20%3A%3A%20%5B%5BBob%5D%5D> .

<urn:name:Alice%23Skills> dct:references <urn:token:friend>
  ~ <urn:reference:urn%3Aname%3AAlice%2523Skills:quote:%5Bfriend%5D> .

<urn:reference:urn%3Aname%3AAlice%2523Skills:quote:%5Bfriend%5D> a resource:ResourceReference ;
  resource:source <urn:name:Alice%23Skills> ;
  resource:selector
    <urn:selector:fragment:http%3A%2F%2Ftools.ietf.org%2Frfc%2Frfc5147:line%3D8%2C9> ,
    <urn:selector:quote:%5Bfriend%5D> .

<urn:name:Bob> <urn:token:lives%20in> <urn:name:BobHouse>
  ~ <urn:name:board.canvas%23e7a1c03b9f2d4e10> .
```

Verified with `rdf` 0.5.0: the draft parses, and a SPARQL 1.2 query (`?s ?p ?o ~ ?r . ?r resource:selector …`) gives each asserted triple with its source, line and quote. A query without `~` gives the same results as today.

### Iterations and errors

- v1 put the line number in the reifier IRI (unstable when text moves), used blank-node selectors, and gave containment a blank-node reifier.
- v2 removed line numbers but anchored reifiers on the note. I then said that quote IRIs "can collide" and built an example with 4 wrong rows. The user saw the error: the links are anchored in `## Skills` and `## Work`, so the reifier must use the heading. The collision came from my rule, not from the model. I had copied the rule from parts (see open item below).
- I also gave containment a reifier equal to its own subject, which adds no information. Removed in v3.
- I drifted into implementation topics (serializer, `sparqljs`). The user corrected this: the task is the draft.

### Facts found on the way (not acted on)

- `@rdfjs/serializer-ntriples` 2.x writes invalid N-Triples for a triple term (`<r> rdf:reifies <a> <b> <c> . .`). Tested.
- `sparql-md` depends on `sparqljs` 3.7, a version that predates SPARQL 1.2. Not tested.

### Open in the draft

- Frontmatter: `tags` → `schema:keywords` has no reifier and no quote form for YAML.
- Parts (code block, blockquote) hang from the heading through `schema:hasPart`, but their IRI and `resource:source` use the note. This is not consistent with the reifier rule.
- Whether fields under a heading should move to the note, with the heading only in the annotation. This changes the meaning and the name-join rule.
- Volume: about 6 to 8 annotation triples per data triple, and the text is repeated in the reifier IRI, the quote selector IRI and `oa:exact`.
